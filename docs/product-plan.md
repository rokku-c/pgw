# Personal Gateway 产品与技术方案

更新日期：2026-09-20  
文档状态：产品规划与技术设计；功能描述表示目标能力，不代表已经实现。  
技术方向：TypeScript、Bun、Effect、React、Radix UI、SQLite、MCP TypeScript SDK v2。当前实现采用 TypeORM，通过驱动适配接入 Bun 原生 SQLite；TypeDORM 名称冲突见第 2.1 节。

交付要求：完整首版。本方案全部产品功能纳入同一次交付与验收，技术难度用于明确实现要求，不作为缩减范围或延后功能的依据。国际化、后台调度、调试台与协议治理同属完整产品范围。运行时按需启用、用户授权及外部依赖配置属于使用方式，不代表功能尚未交付。

## 1. 产品定位

Personal Gateway 是本地优先的个人 AI 工作中枢：统一模型入口、统一 Agent 资产、持续理解个人习惯，并将这些理解转化成可控的请求增强。

用户可以更换 Agent、模型和设备，而项目经验、个人偏好、工具资产和工作进度能够持续积累。

产品由七个部分组成：

| 模块 | 核心职责 | 用户获得的价值 |
| --- | --- | --- |
| Gateway | 模型接入、路由、凭据、费用、请求可靠性 | 一个入口使用多个模型服务 |
| Sessions | 会话、轨迹、项目记忆、任务接力 | 找回工作过程并继续执行 |
| Registry | Agent、Skill、MCP、版本、能力目录 | 清楚自己拥有什么、哪些可用 |
| Persona | 个人偏好、纠错、证据、习惯变迁 | Agent 越用越了解自己的工作方式 |
| Policies | 请求个性化、中继控制、权限、隐私、自动化 | 让理解转化为可解释的实际行为 |
| Runtime | 零配置启动、原生控制适配、目标续跑、进程与任务生命周期 | 用统一入口启动和管理不同 Agent |
| Console | 实时观察、搜索、操作、审批、回滚 | 对整个 AI 工作环境保持掌控 |

主要使用场景：

1. Claude Code、Codex、Pi 等客户端经统一入口调用模型。
2. 从一个项目找回跨 Agent 的讨论、决策、工具调用与成果。
3. 查看 Skills、MCP 工具、安装版本、重复项与能力变化。
4. 将已经确认的个人习惯自动应用到合适的请求。
5. 查看习惯如何变化、为什么变化，并纠正错误理解。
6. 在不同 Agent 或设备间交接任务与相关成果。
7. 使用统一 wrapper 启动尚未配置的 Agent，自动应用网关、项目和工具配置。
8. 在明确授权和预算内持续推进目标，或等待事件后再次执行。

### 2.1 ORM 与 SQLite

TypeDORM 官方定位是 DynamoDB ORM；它与 TypeORM 是不同项目。[T1] TypeORM 官方文档提供 SQLite 驱动方案，包括 `better-sqlite3`。[T2]

SQLite 是已确定的存储要求。ORM 决策需要确认用户所说的 `typedorm` 是否实际指 `typeorm`，不能静默替换名称。若选择 TypeORM，实施前确认 Bun、ORM、SQLite 驱动的具体版本、事务、迁移及部署兼容性，再锁定依赖。

当前实现验证了 Bun 1.3.4 无法加载原生 better-sqlite3，因此使用 TypeORM 提供的自定义驱动入口适配 `bun:sqlite`，保留真实 SQLite 文件与 TypeORM Repository。数据库访问、事务、索引和迁移拥有单一管理入口。此为实现选型说明，不表示 TypeDORM 本身支持 SQLite。

### 2.2 MCP 版本边界

本方案中的“v2”指官方 TypeScript SDK 主版本。2026-09-18 核对时，官方仓库将 v2 标为稳定发布线，拆分为 `@modelcontextprotocol/client`、`@modelcontextprotocol/server`，实现 `2026-07-28` 协议。[T3]

产品分别记录 SDK 版本、协商后的协议版本、Server 自报版本、实际安装包版本和工具 schema hash。不同层级的版本不能混为一个字段。

### 2.3 实现组织

以模块化单体承载 HTTP API、管理控制台、后台任务与 MCP 入口。模块边界按真实业务划分，后端异步执行由 Effect 管理，前端保留常规 React 状态与数据流。

难度定义：低为明确的数据管理与展示；中为多来源接入、状态同步或后台处理；高为协议语义、复杂恢复、跨 Agent 兼容、可靠推断或副作用控制。

### 2.4 国际化

控制台支持 `zh-CN` 和 `en-US` 两种语言。产品文案通过命名 key 引用，例如 `nav.models`、`page.sessions.title`、`common.cancel`，不以英文显示文本作为代码标识，也不将模型名、Provider 名、项目名和用户数据放入翻译表。

语言来源依次为用户已保存选择、浏览器语言、`zh-CN` 默认值。选择持久化在本地浏览器并在同源标签页间同步；切换不重置页面或表单输入。日期、数字、费用和相对时间使用当前语言格式化。CLI、API 字段和模型协议保持稳定，不随界面语言改变。翻译表只保留实际使用的短标签、状态、操作和必要错误/安全警告，不加入冗长产品说明。翻译key及插值参数做静态类型与目录一致性校验，无障碍标签和对话框操作同样纳入双语。

## 3. 模型网关

| 功能 | 为什么应该有 | 实现方式 | 难度 |
| --- | --- | --- | --- |
| 多协议入口 | 保留不同 Agent 的原生使用习惯 | Responses、Chat Completions、Anthropic Messages、Gemini 原生入口 | 高 |
| Provider 与凭据管理 | 集中管理多个服务商及账户 | Provider 配置、凭据引用、授权状态、连通性检查 | 中 |
| 模型目录与别名 | 用任务意图表达模型需求 | `coding`、`fast`、`deep`、`private` 映射为版本化路由 | 中 |
| 能力感知路由 | 避免将请求发给不支持所需能力的模型 | 记录工具调用、视觉、结构化输出、推理、上下文及状态能力 | 高 |
| 客户端和项目身份 | 将成本、权限和路由落到具体工作 | 为客户端分配独立网关凭据，结合显式项目与会话标识 | 中 |
| 会话粘性 | 保持状态和行为连续 | 绑定 Provider、模型及策略快照，切换时检查兼容性 | 高 |
| 流式可靠性 | 流中断、取消和慢客户端都需要明确行为 | 保留事件顺序，处理背压、断连取消、空闲超时和终止状态 | 高 |
| 故障恢复 | 上游异常时持续恢复且可解释 | 可选无限重试、退避与抖动、熔断、负载调度、兼容回退及每次尝试记录 | 高 |
| 用量与预算 | 看清花费并控制自动化开销 | 原始 usage、价格快照、估算标识、项目预算和并发预算预留 | 中 |
| 请求解释器 | 明确网关对请求做了什么 | 展示路由、策略、增强差异、脱敏、耗时与上游去向 | 中 |
| 接入助手 | 降低配置错误和迁移成本 | 配置预览、差异、备份、确认应用、恢复和连接诊断 | 中 |

Provider 目录应覆盖 OpenAI、Anthropic、Google、OpenRouter、国内常用服务、本地模型服务和自定义兼容端点。每个接入显示已确认的协议能力，不能仅凭“兼容”名称判断可用性。

### 3.1 转发和恢复语义

优先保持原生协议与必要元数据。跨协议转换使用显式能力矩阵，无法保持的语义需要明确反馈；默认行为是拒绝该次转换。允许用户显式开启的降级（丢弃推理内容、忽略托管工具声明）必须逐次记录在该次尝试的路由决策中，使丢失可审计，而不是变成静默的能力或内容缺失。

每次上游尝试区分以下阶段：尚未提交、已提交但结果未知、已开始输出、已完成或失败。已有输出的请求保持该次尝试的身份，重试形成新的尝试记录。涉及上游状态、费用或工具副作用的操作，需要结合幂等能力和明确授权决定是否重试。

状态型请求、响应 ID、缓存键与会话归属一起记录。回退目标必须满足隐私、模型能力和上下文状态要求。

### 3.2 接入覆盖

每个客户端分别报告配置可见、API 可代理、会话可读、工具调用可观察、恢复入口可用等能力。API Key 接入与客户端订阅登录分别确认覆盖范围和认证方式。

网关只能治理经过自身的请求和工具调用；界面明确展示实际覆盖情况、缺失原因和补充接入方式。

### 3.3 默认协议前缀

网关的默认入口按客户端协议区分，而不是按最终服务商区分：

| 协议族 | Base URL | 请求端点 |
| --- | --- | --- |
| OpenAI | `/providers/openai/v1` | `/responses`、`/chat/completions`、`/models`、受支持的响应管理接口 |
| Anthropic | `/providers/anthropic` | `/v1/messages` |
| Gemini | `/providers/google` | `/v1beta/models/:model:generateContent`、`:streamGenerateContent` |

`/providers/openai/...`表示按OpenAI协议接入，不限制实际目标一定是OpenAI。模型映射和协议转换可以将其发送到Anthropic、Gemini或兼容服务。

控制台复制入口、wrapper自动配置和托管运行均使用新前缀。既有`/v1/...`和`/v1beta/...`作为兼容入口保留，进入同一认证、策略、计费和路由链路，避免出现双套行为。

### 3.4 模型映射、负载均衡与路由

每个逻辑模型维护独立的目标池：目标包括服务商、实际模型ID、协议、权重、优先级、并发上限、能力声明及健康状态。

| 功能 | 为什么应该有 | 实现方式 | 难度 |
| --- | --- | --- | --- |
| 模型映射 | 客户端使用稳定名称，后端模型可独立调整 | 一个逻辑名称映射一个或多个真实模型，保存版本及变更记录 | 中 |
| 加权轮询 | 多账户、多端点按容量分摊 | 对健康且符合能力的目标进行持久轮询，权重参与选择 | 中 |
| 最少在途 | 长短请求混合时降低排队 | 按目标在途数、并发上限与权重选择，尝试结束释放占用 | 中 |
| 主备优先级 | 保留明确首选供应商及灾备目标 | 按优先级选择目标，同级再负载均衡；不健康目标进入冷却 | 中 |
| 条件路由 | 不同项目、客户端、任务需要不同目标 | 规则匹配身份、项目、模型、内容模态及工作模式，展示命中原因 | 高 |
| 会话绑定 | 有状态响应不能随意换到其他目标 | 绑定服务商、凭据身份、模型与协议转换状态；不兼容切换必须明确中断 | 高 |
| 路由预览 | 修改规则前知道实际影响 | 仅执行匹配与能力校验，展示目标、跳过原因、映射和转换计划 | 中 |

### 3.5 无限自动重试

重试策略支持关闭、固定次数和无限次数。无限模式的`maxAttempts`为null，表示不以次数结束；指数退避、抖动、Retry-After、并发和预算约束仍生效。

可恢复错误进入等待后继续调度；配置、认证或权限需要处理时进入相应等待状态。用户可取消、暂停、修改策略或更新凭据后唤醒。界面显示累计次数、最近原因、下一次时间和已消耗费用。

每次重试拥有独立Attempt，统一归属Request。已向上游提交但结果未知、有工具副作用、或者已经向客户端输出的流，不能作为无副作用请求偷偷重放。流已经开始时，以明确失败/续跑任务呈现后续尝试；任务式调用通过ID和事件序号恢复，不拼接不同模型的两份答案。

无限等待和重试由持久后台任务承载，不用前端循环发请求，也不保持无界内存队列。关闭页面不改变后台任务的授权和状态；撤销调用权限会停止后续尝试。

### 3.6 模型API双向转换

Responses、Chat Completions、Anthropic Messages与Gemini使用统一消息/内容块中间结构转换，同时保留原始协议扩展。转换覆盖请求、响应、流事件、工具调用、工具结果、结束原因、usage和错误结构。

| 能力 | 要求 | 主要难点 |
| --- | --- | --- |
| 文本和多轮消息 | 保持角色、顺序及消息边界 | 各协议system/developer和连续同角色规则不同 |
| 工具调用与结果 | 保持调用ID、参数和对应关系 | 多工具并行、增量参数、嵌套结果 |
| 图片/音频等内容块 | 在目标支持时转换，并保留类型与引用边界 | 编码、URL/data格式和大小限制 |
| 结构化输出与推理 | 按能力映射已公开字段 | 不透明推理状态、签名块和约束差异 |
| 流式响应 | 输出目标客户端协议需要的完整事件生命周期 | 增量文本、工具参数、终止及取消 |
| 状态型会话 | 明确转换状态和可恢复边界 | previous_response_id、上游会话身份与缓存 |

转换器必须报告能力差异：可以等价转换的直接转换；需要用户允许降级的显式说明；无法保持语义的返回具体错误，不能静默丢弃工具、签名或上下文。调试台可以查看转换前后的差异。

### 3.7 全链路调试台

模型调用、MCP工具/资源/提示词、路由预览和Agent控制调用统一纳入调试入口。

- 模型调试：选择入口协议和逻辑模型，编辑请求，流式运行、停止、再次运行，查看每次尝试。
- 工具调试：由schema生成输入入口或JSON编辑器，经同一授权和审批链路执行；有副作用的操作每次确认。
- 请求查看：原始输入、增强后输入、协议转换、上游目标、请求头脱敏视图、响应/事件、错误和耗时逐层展开。
- 请求重放：显式创建新的请求与尝试，保留原请求关联；不会沿用旧审批或静默重复工具副作用。
- 默认保存元数据；开启正文留存后加密保存输入与输出，并设置保留期限。调试任务明确授权保存其调试内容，凭据始终脱敏。
- 成本、预算、熔断、路由和审计逻辑与真实Agent请求共用，避免调试通过但实际调用行为不同。

主要UI由协议选择、模型选择、请求编辑器、运行/取消、响应和轨迹组成；说明放入必要的权限确认和错误状态，不堆积引导文案。

## 4. Agent 与 Session 中心

| 功能 | 为什么应该有 | 实现方式 | 难度 |
| --- | --- | --- | --- |
| Agent 发现 | 了解安装和运行状态 | 已授权目录、配置位置、可执行文件与运行实例 | 中 |
| 能力和版本矩阵 | 升级后可以定位变化 | 安装版本、解析器版本、来源、能力状态分别记录 | 中 |
| 全局会话索引 | 汇集分散的工作历史 | 首次扫描、增量游标、文件轮转处理、重复事件识别 | 高 |
| 统一事件时间线 | 理解完整工作过程 | 消息、工具、压缩、分支、模型切换与成果统一关联 | 高 |
| 项目聚合 | 同一项目可能跨多个目录和 Agent | 仓库、worktree、工作目录、远端标识与人工绑定 | 中 |
| 请求与会话关联 | 把费用和错误定位到具体任务 | 优先显式 ID；推断关联标明依据和置信度 | 高 |
| 搜索与恢复 | 找回过去决策并继续工作 | 后台原文件搜索、字节定位、原生恢复与交接包 | 中至高 |
| 采集完整度 | 避免把缺失数据误认为没有活动 | 展示发现、解析、同步、受限、未知和过期状态 | 中 |

Session 保留原生身份和来源。归一化事件保留原始事件引用、解析器版本及字段缺失原因；未知内容不能补写成已发生事实。

文件采集采用监听与周期核对结合，支持追加读取、截断、重命名和部分写入。扫描限定在授权路径内，读取失败不会触发全盘扩展。

原始对话导入、搜索、学习和外发分别授权。元数据模式与正文模式分开设置，正文保留期限、脱敏和删除范围可配置。

## 5. Skills、MCP 与版本资产

### 5.1 Skills

| 功能 | 为什么应该有 | 实现方式 | 难度 |
| --- | --- | --- | --- |
| 多来源发现 | Skills 散落在全局、项目和插件中 | 授权路径扫描、manifest 与 `SKILL.md` 解析 | 中 |
| 去重和冲突识别 | 同名内容可能不同，相同内容也可能多份安装 | 来源身份、内容 hash、名称和作用范围共同判定 | 中 |
| 版本与内容差异 | 理解升级带来的行为改变 | 版本号、Git commit、内容快照、差异与恢复 | 中 |
| 依赖和权限展示 | 安装前了解所需命令、文件及外部服务 | 静态信息、声明权限、人工确认与运行证据 | 中 |
| 项目级分发 | 同一套能力可用于不同 Agent | 任务或项目 Skill 集，经 Agent 适配器生成原生配置 | 中 |
| 使用反馈 | 找出有价值和需要更新的技能 | 显式加载与调用证据、反馈、失败原因和过期提醒 | 中 |
| Skill 生成 | 将重复工作沉淀为可复用流程 | 从授权轨迹生成草稿，附来源、适用范围和确认流程 | 高 |

版本号、内容身份、修改时间分别存储。静态存在不代表被加载，被加载也不代表实际使用，展示时保留证据等级。

### 5.2 MCP

网关同时承担 MCP Client 与 MCP Server 角色：向下连接已有服务，向上暴露经过筛选的统一工具入口。

| 功能 | 为什么应该有 | 实现方式 | 难度 |
| --- | --- | --- | --- |
| 配置发现 | 汇总不同 Agent 的工具入口 | 解析授权配置，记录来源、作用域和凭据引用 | 中 |
| 主动探测 | 确认真实连接状态和能力 | 授权后连接或启动服务，initialize 与目录查询 | 中 |
| 统一工具目录 | 发现工具及参数能力 | Tools、Resources、Prompts 目录和命名空间 | 中 |
| schema 变更 | 工具升级可能改变行为 | schema hash、结构化差异和依赖影响提示 | 中 |
| 项目工具集 | 限定任务可使用的能力 | 项目级授权、工具筛选、策略快照和动态刷新 | 高 |
| 调用治理 | 控制重要动作与副作用 | 参数校验、超时、取消、审批、结果记录和审计 | 高 |
| 认证与隔离 | 避免多个服务共享过量权限 | 服务独立凭据、授权范围、刷新和撤销 | 高 |

读取 MCP 配置与启动 MCP 进程是两种操作。主动探测需要授权；即使只查询目录，进程启动也可能产生副作用。Server 自报的只读标记作为参考信息，由用户策略和实际边界控制权限。

### 5.3 版本探测

探测来源包括可信可执行文件的版本输出、包管理元数据、Git 版本、manifest、协议握手和文件内容 hash。

每项记录：组件身份、版本类别、检测值、证据来源、检测时间、检测方式、可信程度、失败原因。

被动读取和执行探测分开；执行使用可信路径和参数列表，限制时间与环境变量。远程更新检查单独授权，并记录注册表来源和查询时间。

## 6. 个人习惯与变迁

### 6.1 四层偏好

| 层级 | 示例 | 生命周期 |
| --- | --- | --- |
| 长期偏好 | 中文交流、结论直接 | 长期有效，可撤销 |
| 项目约定 | 当前项目使用 Bun 和 SQLite | 随项目变更 |
| 场景偏好 | 产品讨论充分展开，代码总结简洁 | 按任务匹配 |
| 临时要求 | 本次先分析，暂时不修改文件 | 本次任务或会话 |

偏好应表达条件与例外。例如“代码修改时简短总结”与“产品规划时完整展开”可以同时成立。

### 6.2 证据与生命周期

每条偏好包含内容、作用范围、明确表达或推断、来源证据、反例、置信度、首次观察时间、最近确认时间、有效区间、冲突关系和自动应用授权。

生命周期为：观察、候选、确认、生效、待复核、替代或失效。

学习采用规则提取、异步归纳与用户纠正结合。明确表达形成可确认候选，推断需要跨会话证据。置信度同时考虑证据独立性、时效和覆盖度，避免重复记录让分数虚高。

用户表达、模型输出、外部文档和工具结果分别标记来源。外部内容中的指令不能自动成为用户偏好。敏感信息默认排除于偏好提取之外，外部模型参与归纳需要数据外发授权。

### 6.3 习惯变迁时间线

产品回答以下问题：

- 哪些偏好近期发生变化？
- 变化是全局性的，还是当前项目造成的？
- 哪些偏好已经过期或长期未确认？
- 用户反复纠正 Agent 的问题是什么？
- 哪些新习惯值得形成长期规则？

时间线展示原偏好、新候选、适用范围、证据、反例与确认状态，同时显示采集覆盖度，避免把数据缺失视为行为变化。

### 6.4 个人记忆控制台

应支持查看、修改、锁定、暂停、作用域调整、撤销学习、删除证据及派生记忆，以及临时会话模式。偏好和策略采用版本化记录，请求保存使用的版本引用。

整体难度为高。主要难点是作用域判断、可靠证据、冲突消解与可撤销性。

## 7. 请求个性化

请求个性化将已授权的习惯与项目上下文补充给模型，保留用户原始意图和协议语义。

### 7.1 处理流程

```text
原始请求
  → 识别项目与任务
  → 匹配已授权偏好
  → 检索相关项目记忆
  → 检查冲突与隐私
  → 生成最小增强内容
  → 适配目标 API
  → 记录差异、依据与策略版本
```

示例：原始请求为“帮我实现这个页面”，增强内容可以是“复用当前项目组件，遵循已确认的深色科技风格，以中文简要总结修改”。原始请求与增强内容分别保存或按留存策略记录引用。

### 7.2 运行方式

| 方式 | 行为 | 适用情况 |
| --- | --- | --- |
| 建议 | 展示补充内容，由用户采用 | 新偏好、低置信度判断 |
| 自动补充 | 添加已确认且匹配的上下文 | 语言、输出格式、项目约定 |
| 语义改写 | 在明确授权范围内组织请求表达 | 稳定工作流和结构化任务入口 |

### 7.3 应用规则

1. 当前明确要求优先于历史推断，偏好不会覆盖宿主权限和安全约束。
2. 项目、任务和全局偏好按明确范围匹配，冲突需要解释。
3. 保持消息角色、工具调用 ID、消息顺序、签名块和不透明状态完整。
4. 同一轮工具调用链采用固定策略快照，策略更新在合适边界生效。
5. 每次增强支持差异查看、关闭、纠正与回滚。
6. 增强具有延迟、token 和费用预算，缓存按项目与权限隔离。
7. 个性化失败可退回原请求；权限或隐私检查失败应阻止外发。
8. 对状态型接口，通过适配器管理会话上下文，避免重复注入和缓存失效。
9. 原始请求及 diff 的留存同样受到正文采集授权约束。

这部分难度为高。重点是保持意图、协议正确性、来源可追溯及用户控制。

### 7.4 中继控制：区分行为影响和执行控制

将这项能力定义为 Relay Control。它由网关策略、Agent 原生控制接口和运行监督器共同实现，而不只是替换 prompt。

| 控制层 | 能做什么 | 实现位置 | 能力边界 | 难度 |
| --- | --- | --- | --- | --- |
| 请求层 | 补充偏好、项目记忆、阶段目标，选择模型与参数 | Gateway + Policies | 属于模型行为引导，不能保证工具行为或主动唤醒已经退出的 Agent | 中至高 |
| 运行时层 | 提交下一轮、调整当前方向、取消、恢复会话 | Agent Adapter + 原生控制接口 | 取决于目标 Agent 和版本，权限请求仍需原生审批 | 高 |
| 执行边界层 | 控制被管理工具、文件和网络的实际权限 | Agent 沙箱、工具授权、MCP 审批 | 只对接入该边界的动作形成强约束，修改模型可见工具列表不等于撤销执行权限 | 高 |
| 监督层 | 判断目标进度、安排续跑、恢复进程、执行预算和停止规则 | Runtime Supervisor | 保留用户停止和原生阻塞状态，结果未知时先核对再恢复 | 高 |

网关只能在实际经过自身的请求上应用策略。Agent 等待输入、进行本地计算或已经结束时，需要运行时接口启动下一步。代理层不能通过保持 HTTP 连接或改写结束标记可靠实现持续执行。

模型响应保持角色、事件顺序、工具参数、签名内容和结束语义；控制器产生的后续指令标记为控制事件，记录授权来源，不伪装成用户临时输入或真实工具结果。对已流出的内容，策略变化在下一个受支持的回合边界生效；原生支持 steering 时使用对应接口。

### 7.5 中继控制的产品价值

| 功能 | 为什么应该有 | 实现方式 | 难度 |
| --- | --- | --- | --- |
| 工作模式切换 | 在规划、执行、审查等阶段保持不同要求 | 版本化策略切换，绑定项目和阶段；权限变化通过原生设置确认 | 中 |
| 个人习惯实时生效 | 已确认的偏好无需重复输入 | 请求增强或原生上下文入口注入，保留差异与策略版本 | 中至高 |
| 偏航提醒 | 任务执行可能偏离当前目标 | 从授权事件识别明确偏差，产生带证据的调整建议或已授权 steering | 高 |
| 目标续跑 | 一轮回答结束不代表工作目标完成 | 原生目标模式优先；监督器根据完成事件决定继续、等待或结束 | 高 |
| 暂停与人工接管 | 用户可以随时调整任务方向 | 原生中断、控制事件、审批等待和明确恢复入口 | 高 |
| 自动等待与恢复 | 外部依赖、额度和临时故障需要不同处理 | 分类状态、退避和事件唤醒，恢复前核对授权与执行状态 | 高 |
| 场景化模型调度 | 不同阶段可以有不同的能力和预算要求 | 在可切换边界变更兼容路由，保留上下文和费用归属 | 高 |
| 统一运行解释 | 用户需要知道为何继续或停止 | 显示每轮触发原因、目标进度、预算、停止依据及下一步 | 中 |

### 7.6 持续运行的两种产品模式

**目标模式：**围绕一个明确任务持续推进，直到满足完成条件、用户停止、达到资源上限或进入需要处理的阻塞状态。

**值守模式：**进程可以常驻，但在没有事件时休眠。文件变化、任务队列、时间计划或经授权的外部事件触发一次有预算的工作，完成后重新等待。

持续运行由明确状态机管理：

```text
queued → starting → running → evaluating
                         ├─ 已满足条件 → completed
                         ├─ 有下一步且预算允许 → running
                         ├─ 需要输入或授权 → waiting_for_input
                         ├─ 等待事件或可恢复依赖 → waiting_for_event
                         ├─ 用户暂停 → paused
                         ├─ 无进展或不可恢复问题 → blocked / failed
                         ├─ 达到资源上限 → budget_exhausted
                         └─ 用户停止 → cancelled
```

普通一轮结束可以触发目标评估；用户停止、原生审批拒绝、安全阻塞和达到循环保护上限不能被当作普通结束再次自动续跑。用户取消后撤销相应唤醒任务，自动恢复只用于事先授权且状态明确的异常。

每个任务具有目标、完成依据、最长时间、最大回合数、费用与 token 预算、并发上限、可用工具、等待策略和恢复授权。预算由运行时及网关共同强制，包含子任务和评估模型开销，不能只写成一段提示词。

评估先使用可直接观察的任务状态和成果，再结合有来源的模型判断；不能仅因为 Agent 自称完成就覆盖缺失的依据。进展判断结合成果变化、剩余事项、重复输出和重复失败，重复动作不能自动被视为进展。

任务状态和控制事件持久化。使用任务租约防止多个监督器重复续跑，记录原生 session、thread、turn 和进程身份；恢复先核对正在执行的工作与副作用，再决定续接或创建新尝试。

### 7.7 复用原生控制能力

| Agent | 已核实的官方入口 | 本产品适配方向 |
| --- | --- | --- |
| Claude Code | `/goal` 按条件跨轮工作；Stop hooks 提供结束时控制；目标模式保留权限要求 [A3][A4] | 优先使用原生目标模式，统一外层预算、状态、成果与接管；自定义策略按版本适配 hooks |
| Codex | App Server 提供 `turn/start`、`turn/steer`、`turn/interrupt` 和 thread 生命周期接口 [C2] | 托管执行通过结构化协议控制，显式处理审批、输入请求与中断 |
| Codex 非交互入口 | `codex exec --json` 输出事件，`exec resume` 可以恢复指定会话 [C3] | 用于边界明确的批次工作；需要细粒度控制时采用 App Server |
| Pi | RPC 模式支持消息、steer、follow_up、abort 与事件通知 [P1] | 使用 RPC 驱动托管任务，按目标版本处理运行结束和交互请求 |

原生持续机制与外层监督器明确分工，同一回合只由一个控制方决定启动下一轮。原生目标的完成、失败和防循环决定会向上同步；外层控制器不通过重启绕过这些决定。

每个适配器报告原生目标、下一轮启动、当前轮 steering、中断、恢复、审批桥接和后台执行能力。能力缺失明确展示，不能根据可以代理 LLM 请求推断全部控制能力可用。

## 9. Harbor 调研与吸收方案

### 9.1 结论

本方案吸收 Harbor 的设计，并将其运行器适配纳入完整首版。Harbor 是 Agent 执行与评估框架。安装文档采用 Python 包管理器，默认执行环境为 Docker sandbox，也支持其他 sandbox。[H1] 它围绕任务、Agent、运行环境、执行尝试、作业和轨迹组织能力。[H2]

本项目继续采用 TS/Bun 主技术栈，同时实现 Harbor 领域概念与交换格式的适配，并提供可由用户启用的外部运行器。Harbor 管理显式提交的运行，Personal Gateway 管理个人日常流量、存量会话和长期资产，两者职责互补。

### 9.2 值得吸收的设计

| Harbor 设计 | 官方能力依据 | 对本产品的价值 | 吸收方式 | 难度 |
| --- | --- | --- | --- | --- |
| Task / Trial / Job | 任务定义与执行尝试、批量作业分开 [H2] | 一个目标可多次尝试，每次结果和成本独立 | 区分 Task、TaskRun、BatchRun 与上游请求尝试 | 中 |
| ATIF | 使用统一 JSON 表示轨迹 [H3] | 会话查看、比较和交换有稳定边界 | 原生事件保真存储，增加 ATIF 导入导出适配 | 中至高 |
| Agent 能力矩阵 | 分别声明轨迹、恢复、加载、MCP、Skills 能力 [H4] | 接入状态真实、可解释 | 每个适配器报告能力、证据、版本和限制 | 中 |
| 轨迹加载 | 支持的 Agent 可从原生或 ATIF 轨迹加载上下文 [H5] | 项目交接具有结构化入口 | 按目标能力选择原生恢复、轨迹导入或摘要交接 | 高 |
| Handoff | 把支持的运行会话接回本地 CLI [H6] | 远端工作可返回日常工具继续 | 会话交接与文件恢复分开授权和展示 | 高 |
| 任务级 Skills | 将技能集提供给 Agent 适配器 [H7] | 同一任务可携带确定的能力版本 | Skill 集生成内容清单和快照，再映射到客户端 | 中 |
| Artifacts | 收集运行产生的文件 [H8] | 成果从聊天记录中独立出来 | 文件清单、内容 hash、预览、导出和项目关联 | 中 |

以上是吸收建议，不代表本产品已实现相同能力，也不代表引入框架即可自动获得全部 Agent 兼容性。

### 9.3 轨迹互操作

ATIF 作为交换格式，内部使用可增量写入的事件模型。每次转换记录输入格式、schema 版本、适配器版本、字段映射与转换损失。导出时保留工具调用和结果之间的引用，对分支、子会话及附件按目标格式能力映射。[H3]

规范化轨迹只能包含来源实际提供且已授权的数据；缺失、私有或不透明内容保留状态，不推测填充。附件导入检查路径、大小、类型与可访问范围。

Harbor 明确区分“生成 ATIF”与“加载 ATIF”两种能力。[H3] 因此本产品分别显示可查看、可导出、可加载、可原生恢复和可交接，避免把格式兼容展示成执行能力兼容。

### 9.4 会话、任务与成果分离

建议关系：

```text
Project
  └─ Task
      ├─ TaskRun
      │   ├─ Session / Trajectory
      │   ├─ Request / UpstreamAttempt
      │   ├─ ConfigSnapshot
      │   └─ Artifact
      └─ Handoff
```

TaskRun 表示一次完整工作尝试，UpstreamAttempt 表示一次模型请求尝试，BackgroundJob 表示采集或归纳等内部任务，三者独立计数。

同一 Agent 原生恢复、跨 Agent 上下文交接和工作文件恢复分别设计。Harbor 当前 Handoff 文档仅列出 Claude Code 支持，且明确恢复的是会话历史而非 sandbox 文件。[H6] 本产品据此要求交接页面展示会话状态、文件基线、未提交修改、目标目录及冲突处理。

### 9.5 内置 Harbor 运行器适配

集成链路建议为：

```text
Console 提交已授权任务
  → 创建 TaskRun、预算和配置快照
  → Harbor 运行器启动独立进程
  → 执行环境内的模型请求接入 Gateway
  → 采集进程状态、原生日志、轨迹和成果
  → 写入本地索引
  → Console 查看、比较或交接
```

落地要点：

- 明确记录 Harbor 版本、任务来源、Agent、模型、环境、Skills 和策略快照。
- 使用参数数组启动可信入口，限定工作目录、环境变量和继承凭据。
- 为每次运行分配受限网关凭据，绑定预算、项目和有效期。
- 配置 sandbox 到网关的明确网络路径；容器内的本地回环地址不能直接作为宿主网关地址使用。
- 任务开始前确认目录挂载、网络、凭据及潜在副作用范围。
- 为日志和产物设置大小、路径及保留策略，导入失败保留可重试状态。
- 整体取消同时管理运行器、执行环境和费用状态，不能仅凭 CLI 退出认定远端执行停止。
- 只有能力矩阵已确认的 Agent 才显示对应导入、恢复与工具配置入口。

集成难度为高，主要成本在执行环境、取消语义、凭据传递、文件生命周期和版本兼容，而不是启动一个命令。

| --- | --- | --- | --- |

           模型 API / MCP
                  │
┌──────────── Bun 服务 ─────────────┐

│                         → 上游    │
│                                  │

### 10.1 请求链路与后台执行

请求链路设定明确的处理预算，流式数据优先转发。扫描、正文索引、习惯归纳和成果导入异步执行，不能拖慢模型响应。

Effect 管理依赖、资源释放、取消、超时、重试和并发。持久任务状态写入 SQLite，记录去重键、租约、尝试次数和恢复状态；进程内队列只承担调度。

有副作用的任务恢复时先核对外部状态，采用幂等键或人工确认。系统承认“结果未知”这一状态，避免重启后盲目重复执行。

### 10.1.1 后台调度与进度

索引、扫描、重建、历史搜索、版本探测、远端目录探测、导入导出和归纳由后台scheduler执行。重操作与实时代理分离，耗CPU的解析和同步SQLite写入放在独立worker/进程，不能只给主线程函数加async就视为隔离。

提交接口快速返回202与任务ID；控制台订阅或查询状态。任务包含类型、授权范围、阶段、已处理数量、总量（可未知）、当前项、心跳、取消请求、结果与错误。无法预估总量时显示处理数量和阶段，不伪造百分比。

- 同一来源/同类操作去重或合并，限制并发，避免多次点击启动重复扫描。
- 取消在处理边界检查，完成后与取消竞争以持久状态为准；禁止报告已取消但仍继续写入。
- 重启恢复由任务类型决定；可幂等扫描可恢复，模型或工具执行结果未知时先核对，不能自动复制副作用。
- 数据写入采用短事务和分批提交；后台worker与主服务读写争用采用退避，网关请求优先。
- 搜索使用后台维护的索引；重查询提交任务执行，返回结果按游标分页。前端防抖及取消过期查询，页面切换不阻塞服务。
- 全局任务面板展示正在处理、等待、失败与完成的任务，支持取消、重试和结果定位。

### 10.2 数据分组

| 分组 | 核心对象 |
| --- | --- |
| 流量 | Provider、Model、Route、Request、UpstreamAttempt、Usage、RouteDecision |
| 资产 | AgentInstallation、AgentCapability、Skill、MCPServer、MCPTool、ComponentVersion |
| 工作 | Project、Task、TaskRun、Session、SessionEvent、Artifact、Decision、Handoff |
| 个性化 | Preference、Evidence、PreferenceRevision、Policy、RequestPatch |
| 治理 | CredentialRef、Approval、AuditEvent、BackgroundJob、ConfigSnapshot、Device |
| 运行控制 | LaunchProfile、ManagedAgentHome、RunGoal、RunCheckpoint、ControlEvent、RunLease |

会话存储遵循 filesystem-first：原生 JSONL 是正文来源，读取和搜索在授权范围内按需打开文件，增量扫描只持久化身份、游标、事件偏移、分支关系等定位信息。SQLite 不重复保存会话正文，也不建立复制正文的 FTS 索引。搜索通过独立 Worker 的持久任务执行，显示扫描进度、支持取消；源文件缺失或变更时明确显示覆盖缺口。偏好仅保存确认所需的短证据，不复制完整会话。实现难度中等，重点是字节边界、文件改写检测、权限撤销及证据可追溯。

旧版重复正文和 FTS 使用显式停服维护回收：取得同一数据库的运行归属锁，核对源文件身份和已索引前缀哈希，清除可重建副本并 VACUUM；源文件缺失、改变或授权停用时保留旧正文，避免丢失唯一副本。服务运行中拒绝压缩，避免长时间持有 SQLite 写锁拖住代理和调度。请求正文留存属于独立的可观测性数据，应与可重建的文件索引分开管理，并设置容量与期限。

逻辑对象随实际功能形成表和索引。原始大文件、附件和可选正文快照存受控内容目录，SQLite 保存权限、引用、索引和内容身份。运行状态持久化记录轮次、预算、唤醒条件、最近进展和原生会话身份，配置实例与会话留存分开管理。

费用同时保留上游 usage、计价版本及计算结果，金额采用确定精度。由会话导入和代理观察获得的同一次消耗需要关联去重，未知 usage 与零消耗分别展示。

### 10.3 存储生命周期

数据库需要迁移、事务、写入并发控制、保留期限、空间限制及一致性备份。全文检索方案需要明确中文处理能力，并支持由原始授权数据重建索引。

删除操作覆盖正文副本、全文索引、派生偏好、摘要、缓存与设备同步记录。备份记录保留期限；恢复备份时应用删除记录，避免让已删除内容重新进入学习流程。

### 13.1 两种接入方式共存

**一键设置：**为用户已有 Agent 安装生成持久配置，预览、备份并确认应用，原生命令随后直接接入网关。

**Wrapper 启动：**命令名暂定 `pgw`，启动时自动准备本次配置、身份和受限凭据，保持原生 CLI 的交互体验。已有配置采用覆盖层；从未配置的 Agent 使用网关托管的专用配置目录或该版本支持的启动参数。

下面为拟议产品命令，不表示当前已经实现：

```sh
pgw claude
pgw codex
pgw pi
pgw --profile frontend claude
pgw codex -- resume SESSION_ID
pgw run codex --goal "完成项目文档的结构整理" --budget-usd 10 --max-turns 20 --timeout 2h
pgw resume RUN_ID
pgw stop RUN_ID
```

Wrapper 自身参数放在 Agent 名称之前；Agent 名称后的参数原样交给目标 CLI，`--` 用于明确透传边界。`pgw run` 则是独立的托管执行子命令，不假装成原生交互模式。

### 13.2 零 Agent 配置启动

产品目标是“用户只配置网关一次，每个 Agent 无需重复配置”。首次启动流程为：

1. 检测 Agent 可执行文件、版本、来源和适配能力。
2. Agent 未安装时，提供官方来源、固定版本和安装位置，确认后安装到受管位置。
3. 检查网关健康；需要时启动本产品拥有的本地服务，并确认实例身份。
4. 选择项目和启动配方，生成 Provider、模型、Skills、MCP 与控制策略快照。
5. 签发绑定本次运行、项目和预算的网关凭据，上游真实密钥保留在网关。
6. 生成专用配置或启动覆盖层，校验最终生效项和现有认证冲突。
7. 在原工作目录启动 Agent，保留必要的终端行为和原生信任确认。
8. 注册受管会话目录与运行身份，自动纳入采集、费用及版本管理。
9. 结束时撤销运行凭据、清理临时文件，并按策略保留恢复需要的会话和配置快照。

零配置以网关已经具备可用模型服务和合法凭据为前提。缺少凭据时由网关引导完成一次授权；本地模型服务则使用其实际认证要求。安装、账户授权、工作目录信任与工具权限分别处理，不能把“自动配置”理解为自动同意所有权限。

### 13.3 各 Agent 的配置适配

| Agent | 已核实的入口 | Wrapper 的使用方式 | 难度 |
| --- | --- | --- | --- |
| Claude Code | 网关地址通过 `ANTHROPIC_BASE_URL`；CLI 有 settings、附加 prompt 与 MCP 配置入口 [A1][A2] | 使用本次启动环境和配置覆盖，明确网关认证方式，按配方映射模型及工具 | 中至高 |
| Codex | `CODEX_HOME`、CLI 配置覆盖、自定义 Provider 与模型配置 [C1] | 新安装使用稳定的受管 `CODEX_HOME`，已配置用户优先使用本次覆盖；保留必要状态目录 | 中 |
| Pi | Provider 和模型配置由原生配置适配器生成；托管控制采用 RPC [P1][P2] | 按实际版本确定配置作用域，登记会话位置和可用扩展 | 中 |

Claude Code 官方文档指出，只设置网关地址而未提供网关凭据时，已有订阅登录可能仍是生效身份。[A1] 因此启动预览必须同时解释地址和认证来源；网关模式、订阅模式及计费归属分别确认。

Codex 自定义 Provider 等配置需要放在受支持的用户级或启动级入口，而不是依赖项目配置覆盖宿主连接信息。[C1] Agent 的配置优先级随版本变化，适配器按检测到的版本生成配置并报告不兼容项。

隔离配置使用 Agent 官方支持的入口，不粗暴替换整个系统 HOME。用户已有 SSH、Git、凭据存储和项目规则保持原有边界；受管目录的全局 Skills、插件及 MCP 配置通过已授权的来源显式导入。受管配置隔离不等于进程沙箱，也不绕过项目或组织策略。

### 13.4 交互式与托管式运行

| 模式 | 交互体验 | 控制方式 | 状态归属 |
| --- | --- | --- | --- |
| 原生交互式 | 保留 Claude Code、Codex、Pi 的原生终端界面 | 默认继承终端与标准输入输出，应用配置覆盖 | 前台 wrapper 管理本次子进程，会话纳入网关索引 |
| 托管目标式 | 控制台或 CLI 展示任务、审批、进度和成果 | 原生 App Server、RPC 或结构化非交互事件 | 网关 Runtime 管理目标、进程和持久状态 |
| 后台值守式 | 查看状态、接管、暂停与恢复 | 授权事件触发有预算的任务 | 服务级生命周期管理，空闲时等待 |

原生交互模式不通过解析终端画面或循环输入“继续”判断任务完成。后台执行通过明确受支持的原生接口实现，终端关闭后的继续行为由启动模式和用户授权决定。

### 13.5 启动可靠性与隔离

- 使用可执行文件路径和参数数组启动，保持参数中的空格与特殊字符，不拼接 shell 命令。
- 交互模式保留退出码、信号和终端状态；需要代理终端时再使用 PTY，并处理尺寸变化。
- 只管理本产品拥有的进程身份，不以端口或同名进程作为终止依据。
- 每个配置作用域有明确身份和并发规则；同一原生 session 同时只允许一个写入控制方。
- 凭据通过受支持的受限环境或凭据入口传入，不写入命令行、导出快照或普通日志；同时承认同用户进程的可见性边界。
- 配置落盘使用受限权限和原子替换，持久配置变更支持备份与恢复。
- 清理仅针对本次产生的临时资源。原生会话、恢复检查点和用户文件按独立保留策略处理。
- 模型别名、辅助模型、MCP、项目规则、认证和组织配置冲突在启动前明确展示。

完整首版同时包含：已安装但未配置 Agent 的启动、缺少 Agent 时的授权安装、已有配置的无损覆盖、原生交互保持、受管会话发现、配置恢复、原生目标执行、审批桥接、状态恢复与后台值守。

### 14.1 完成判定

1. 按“真实入口、真实处理、真实存储或外部执行、可观察结果”形成端到端能力，页面、按钮或模拟数据本身不构成完成。
2. 对每项功能记录完成证据、支持版本、所需配置、权限条件和已知边界。
3. 功能具有对应的失败、取消、恢复和数据保留行为，跨模块状态保持一致。
4. 外部服务或客户端能力限制如实标记。支持范围内缺少实现的项目保持未完成，不能以“暂不支持”视为完成。
5. 用户选择关闭功能或尚未授权，不影响该功能被完整实现；实现缺失与未启用分别展示。
6. 所有范围项满足完成标准后，才将完整首版标记为已交付。

### 14.2 产品质量指标

衡量网关额外延迟、请求成功率、采集覆盖与新鲜度、已知和估算费用比例、个性化纠正与撤销比例、任务接力后的补充上下文量、配置与任务恢复完整度，以及删除操作覆盖率。

运行控制另记录零配置启动成功率、有效配置冲突率、无进展轮数、取消生效时间、重复执行次数与预算偏差。质量指标用于定位问题和确认实际效果，不替代完整功能范围。

### 9.6 请求可观测性

普通模型请求至少保存可定位的元数据：请求组、客户端、协议、模型别名、目标 Provider、路由决策、重试尝试、状态、首字节、总延迟、Token、费用、响应 ID 和错误。正文采集默认开启，用户可以关闭；正文与元数据分开保留，均使用本地加密和期限/容量策略。

正文轨迹拆成 request、effective、upstream、response、output 五个阶段。网关协议转换必须同时展示转换前的上游内容和转换后的输出；流式请求按块异步落盘，允许查看原始 SSE 和转换结果；同一 route session 的请求按顺序关联并提供 effective diff。大请求按分片分页读取，只有用户打开正文查看或 Diff 时才在前端解析结构。所有正文采用本地加密、分阶段大小限制、总容量上限和过期清理。

实现方式：代理线程只发送带序列号的完整事件到 Trace Worker，Worker 串行短事务写入 SQLite，队列满时记录 partial 而不是阻塞模型调用。请求头、Cookie、凭据字段和 URL 参数按原样进入加密记录；脱敏与脱敏映射是独立的查看/导出功能，不修改事实记录。删除、过期和容量淘汰删除正文分片但保留最小状态。难度中高，风险集中在流式背压、取消收尾、加密访问边界和存储配额。

## Agent Trajectory 定义修订

Agent 可观测性按 `docs/agent-trajectory.md` 实施：会话 → 轮次 → 步骤 → 上下文快照 → 模型/工具因果轨迹，三栏浏览与统一 Inspector。旧“混合事件列表 + 全库快照”不再作为该能力的交付标准；快照 Diff 指步骤级上下文、工具、路由与运行状态的语义变化。以 T01–T15 逐项证据判定完成。
